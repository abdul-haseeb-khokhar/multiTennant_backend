# CLAUDE.md: multiTennant_backend

Backend core of a multi-tenant **AI customer-support platform** (call centres and businesses put an AI agent in front of their customers; humans take over when needed). **Voice-first since 2026-10-21 (team-alignment L1):** the main product is an AI phone receptionist that answers from the business's own material and saves appointment and call-back requests that staff confirm; plans are measured in call minutes (L6). Message operations (the chat widget, the staff chat queue, WhatsApp) are halted, not removed (L2): they keep working and get no new work. This repo is the **backend core** only. Full design: [docs/architecture.md](docs/architecture.md). Open decisions with the other teams: [docs/team-alignment.md](docs/team-alignment.md). Read both before building features; the phase plan is in [docs/backend-roadmap.md](docs/backend-roadmap.md).

## Team split
- **Backend core (this repo, Abdul Haseeb):** tenants, auth, users/roles, end customers, keys, channel connections, agent config, plans/usage, gateway + dashboard API.
- **AI engine (Abdullah Younas, separate repo):** conversations, messages, RAG/knowledge chunks (pgvector), LLM, call logs, agent actions, voice. Schema `ai_engine` in the **same Postgres**; separate Prisma project.
- **Frontend (another colleague):** dashboard + widget; consumes this repo's OpenAPI.

## Stack and commands
NestJS 12, TypeScript 6, Prisma 6 (PostgreSQL, schema `tenant_core`), Passport JWT, bcrypt, class-validator/transformer, `@nestjs/config`, `@nestjs/swagger`, Jest 30, oxlint, Prettier (single quotes, trailing commas).

## Rules for this codebase
1. **Tenant isolation is the top rule.** Every query on tenant data includes `tenantId` in the `where`. Services take `tenantId` as the first argument. The tenant comes from the verified JWT/key, never from request content. After a scoped `findOne`, still scope the mutation (`update({ where: { id, tenantId } })`). Public token flows (invite accept, reset, verification) take the tenant from the record the hashed token belongs to.
2. Tenant-scoped routes live under `/v1/tenants/:tenantId/...` and use `@UseGuards(JwtAuthGuard, RolesGuard)`. `JwtAuthGuard` rejects a token whose `tenantId` differs from the URL (403 `TENANT_MISMATCH`) and a suspended tenant (403 `TENANT_SUSPENDED`). `RolesGuard` fails closed: every handler needs `@Roles(...)`. Platform-admin routes (`/v1/admin/...`) use `PlatformJwtAuthGuard`; the two token kinds are not interchangeable (`scope` claim: `tenant` or `platform`). `request.user.role` comes from the database (JwtStrategy), not from the token. Staff and platform tokens carry `iatMs` (milliseconds) and are refused when issued before the user's `password_changed_at` or `tokens_valid_after` (logout, J1): compare only through `wasIssuedBefore` (`auth/token-freshness.ts`).
3. Never return `passwordHash` or `tokenHash`; use `omit: { passwordHash: true }` / `omit: { tokenHash: true }`.
4. Map Prisma errors in the service with `isPrismaError`: `P2002` → 409, `P2003`/`P2025` → 404 (`P2003` on tenant delete → 409 `TENANT_HAS_DEPENDENCIES`). Throw `ApiException(status, ErrorCode.X, message)` so the body is `{statusCode, code, message}`; add new codes to `common/errors/error-codes.ts` **and a translation to `src/lang/en/errors.json` and `ur/errors.json`** (a unit test fails otherwise) and never rename one (the frontend translates them).
5. **One writer per table.** Do not write to `ai_engine` tables; do not declare `ai_engine` models in this Prisma schema.
6. New tables go in schema `tenant_core` (`@@schema("tenant_core")`, `@@map` snake_case, columns `@map` snake_case).
7. Match surrounding style; run `npm run lint`, `npm test`, `npm run test:e2e` and `npm run build` before finishing. Lists return `{data,total,skip,take}` (default `take` 20, max 100). After changing a route or DTO run `npm run openapi:export`.
8. Role matrix (B2) as built: owner and admin invite staff and manage users (email, role, status, delete); an admin cannot invite, change, disable or delete an owner or promote anyone to owner; a tenant always keeps one **active** owner; every role reads users and reads, creates and edits customers; only owner/admin delete customers and read the audit log. Roles are `owner`, `admin`, `agent`. Nobody sets another person's password (invite, reset). Nobody disables, demotes or deletes themselves (403 `CANNOT_MODIFY_SELF`, J4; the last-owner rule stays for races). Every tenant route is listed with its allowed roles in `test/role-matrix.e2e-spec.ts`: add the row when you add a route.
9. Emails are stored trimmed and lower-case (DTO `@NormalizedEmail`, services normalise too, and a DB CHECK constraint enforces it): normalise any new email input. A change that must not be half-done (role or status change plus its audit entry, the last-owner check) runs in one transaction and passes `tx` to `AuditService.record`. Never put tokens, hashes or links in logs (only `ConsoleMailer` may log a link) or in audit `before`/`after` (keys such as `password`, `token`, `hash`, `link` are stripped anyway).
10. **Billing (section I, Phase 2B).** The `subscriptions` row is the source of truth; `tenants.plan` and `tenants.status` are **denormalised mirrors** (`status`: `trial` = on Starter, `active`, `suspended`, `closed`) written ONLY by `SubscriptionService`, in the same transaction as every subscription change. Never write them anywhere else and never read them to decide what a tenant may do (ask `EntitlementsService.check`); the only reader is the auth guard (suspended/closed). Every change to a subscription is a normalised billing event through `SubscriptionService.applyEvent` (idempotent by provider event id, one transaction: state, invoice, append-only `billing_events` row, audit entry, mirrors). Transitions live in the pure `state-machine.ts`; add a transition there with a table test, never inline in a service. Time comes from the injectable `Clock`; code that reads a subscription uses `getEffective` (applies due transitions on read), never the raw row. Amounts are integer minor units plus a currency code, never floats. Entitlement keys and shapes: `billing/entitlements/entitlements.ts`. Nothing outside `ManualProvider` and `BillingProviders` may name a payment company (a unit test scans `src/`). `data_use_consents` only records the choice: no training export may be built before the legal review (I11). **Overage (J6, Phase 4B):** `subscriptions.overage_enabled` (default true) is a setting, not a state: changed only by `SubscriptionService.setOverageEnabled` (owner route, row lock, `overage.changed` billing event + `billing.overage_changed` audit entry in one transaction), meaningful only when the entitlements have `overageConversationMinor` (`overageSettings()`); `check('conversations')` then allows past the included amount with `overage: true`, never while `past_due`, never for seats or knowledge. The overage count is derived, never stored (`OverageService`: `max(0, used − included − conversations held for a human)`); an invoice stores only what the admin recorded. The 100% reminder is `usage.overage_started` or `usage.limit_reached`, never both for one state. **Call minutes (L6, Phase 5A):** the entitlements `callMinutesPerPeriod` (null = unlimited, missing = 0), `callMinutePeriod` (`total` | `month`, default `month`) and the price `overageMinuteMinor` sit next to the conversation keys; `check('callMinutes')` asks "may one more minute be served?" and reads `usage_daily.call_minutes` through `UsageProvider`. The owner's single `overage_enabled` switch governs BOTH units: a plan has the switch when it prices extra minutes OR extra conversations (`OVERAGE_NOT_AVAILABLE` otherwise) and overage applies to a unit only with that unit's own price (`overageApplies`); `past_due` is served within the limit and never starts overage, for minutes as for conversations. `OverageService.callMinuteSummary` derives `max(0, used − included)` (no "held for a human" for minutes); `GET …/billing` carries `usage.callMinutes`, `subscription.overage` has `minutePriceMinor`. Reminders `usage.minutes_threshold|overage_started|limit_reached` are deduped per unit and period, one 100% message per state. Minutes are written only through `UsageService.recordCallMinutes` (ledger kind `call`, once per call id): no public route writes them, and the engine's call-usage event is acknowledged only until Phase 5E.
11. **Gateway and widget (Phase 3; halted by L2: no new work).** Widget routes (`/v1/widget/*`) are public and take the tenant ONLY from the widget key (session) or the signed widget token (everything else), never from the body, URL or message text; the engine's `X-Tenant-Id` is that same verified value. The widget token has `scope: "widget"`, claims `tenantId`, `endCustomerId`, `conversationId`, `keyId`, is signed with a secret derived from `JWT_SECRET` (so staff and platform guards cannot accept it and it cannot pass as one), and `WidgetAuthGuard` re-checks the key (revoked?) and the request `Origin` against that key's `allowed_origins` on EVERY call; a missing Origin is refused. A widget key is public, not a secret; it is stored as sha256, shown once, never logged. Conversations are looked up by tenant AND end customer AND conversation id. **The end customer is never dropped (I5, D7):** a suspended/closed tenant or a plan without chat answers `200 {status:"blocked"}` with a fallback text and no token; a plan limit stores the message with `aiReply:false`, escalates with `limit_reached` and never calls the model; a slow or failing engine ends in `fallback ai_unavailable` plus an escalation (remembered in `gateway_conversations.escalation_pending` if the engine cannot be told). Fallback reason codes (`service_unavailable`, `limit_reached`, `ai_unavailable`) are stable, translated in the `widget` namespace, and never reveal billing state to the customer. **CORS** for `/v1/widget/*` is decided by `WidgetCorsService` (installed as the `enableCors` delegate in `app.setup.ts`): the preflight is answered only for an origin some active widget key lists (a deliberate cross-tenant boolean lookup, cached and rate-limited), and the real response gets `Access-Control-Allow-Origin` only after key and origin matched for that key; never `*`, never credentials; dashboard routes keep `FRONTEND_URL`. **Usage:** `usage_daily` is written only by `UsageService`, always through the `usage_events` ledger (unique per tenant, kind, engine id), so a conversation or message counts once; `EntitlementsService` reads `conversations` from it (`month` = UTC calendar month, `total` = since the UTC day the period began). The engine is reached only through `EngineClient`; never log message text, tokens or keys; engine error details never reach a customer.
12. **Human hand-off, live streams, notifications (Phase 4; the chat queue is halted by L2, the notification and stream machinery stays in use).** Conversations belong to the engine and are reached only through `EngineClient` (list, counts, claim, release, resolve, human message), always with the tenant of the verified staff token and the acting user's id and role; a conversation id of another tenant is a 404. The role rules live in `ConversationsService` AND are enforced again by the engine: every role may read, claim and work conversations; **only the assignee of a `human_active` conversation may reply, release or resolve it, whatever their role** (409 `CONVERSATION_NOT_ASSIGNED_TO_YOU`), a second claim is 409 `CONVERSATION_ALREADY_CLAIMED` (re-claiming your own is a no-op), a resolved one 409 `CONVERSATION_RESOLVED`; claim, release and resolve are audited (`conversation.claimed|released|resolved`, never message text); disabling or deleting a user returns their chats to the queue (best effort). Dashboard views show an anonymous visitor as `web_ab12cd…` only (`displayExternalId`): the full visitor id is that visitor's secret. **Events** come in at `POST /internal/events` (outside `/v1`, the only such route besides health): HMAC-SHA256 signature over `<timestamp>.<raw body>` with `INTERNAL_API_TOKEN`, 5 minute window; the tenant is the ENVELOPE's and is checked against an existing tenant, ids inside `data` are only looked up scoped to it; the (tenant, event id) row in `engine_events` is written in the same transaction as the effects (idempotent, rolls back whole); live messages and `announce` run after the commit; unknown types are acknowledged and ignored. Message text travels only as `human`/`system` `message.created` and only to the widget stream, never to the dashboard stream, the inbox or a log. **Streams** (`RealtimeHub`, in process): staff stream with Bearer header or single-use ticket (never the access token in a query string), 5 per user (the oldest is closed), re-checks the user every minute, ends after 1 hour; widget stream uses `WidgetAuthGuard` (key + Origin every call), ends with the token and re-checks the key. **Notifications**: one row per recipient created inside the event's transaction (escalated -> all active staff, assigned -> the assignee unless they assigned it to themselves, action.proposed -> owners/admins) or by `BillingRemindersService` from the hourly billing job with a `dedupe_key` (7/3/1 days, grace started, downgraded, 80%/100% of the conversation allowance); text is never stored: the frontend renders `<type>.title|body` from the `notifications` namespace with `params` (documented per type in `notification-types.ts`); every query is scoped to tenant AND user.

13. **Email (H3, Phase 4C).** All mail goes through `MailService` and the `Mailer` token (never call a provider elsewhere). A send failure NEVER breaks the flow that asked for it: `sendNow` returns `delivery: sent | failed | skipped` (invite create, signup `verificationDelivery`, verification resend report it) and `queue` is for the password-reset request, which keeps its constant 202 and must never report a delivery or differ for an unknown account. Never log a recipient address, a link, a token, the API key or the provider's own error text (Resend's test-mode refusal quotes the account's address): log the template and a `MailFailureReason` code. `ResendMailer` retries once, only after a network error, a timeout or a 5xx (same `Idempotency-Key`), never after 4xx/429. Templates render only through `MailRenderer` (escape every value, http(s) links only, no remote content); texts are `email.<template>.*` / `email.layout.*` keys in en and ur. Tests must not send real mail: `test/setup-env.ts` and `test/db/setup-db-env.ts` force `MAIL_PROVIDER=console` because `.env` may hold real settings.

14. **Account decisions (Phase 3C, J1 to J5, J7).** *Logout:* `POST /v1/auth/logout` and `/v1/admin/auth/logout` stamp `tokens_valid_after` (one timestamp per user, so it ends every session of that user); logout uses `SessionAuthGuard` (no tenant-status check, so a suspended workspace's users can still log out). *Slugs:* only `SlugService` decides whether a slug is free or resolves a login slug; a rename keeps the old slug as a `tenant_slug_aliases` row (accepted at login 30 days, reserved 90) and every claim on a slug (signup, rename) takes `SlugService.lock` first (`$executeRaw`: the function returns void). `SLUG_TAKEN` carries `suggestions`. *Email-first login:* the selection token (`scope: "workspace-select"`, 10 minutes, derived secret, user ids only) opens no route by itself; every login request runs exactly `MAX_COMPARED_PASSWORDS` (3) bcrypt comparisons, never one per membership; a wrong password and an unknown email must stay indistinguishable (body and time); `LoginThrottleService` counts only FAILURES, per (email, IP) and per IP, never per email alone (nobody may be locked out from another address) and checks before any lookup. A reset by email (`password_resets.all_workspaces`) is the one deliberate cross-tenant write: the email comes from the reset record's user row, never from the request, and every reset remembers the address it was sent to. *Upgrade requests:* one pending row per tenant (partial unique index), the owner asking again replaces it, handling a request never changes the plan (the subscription routes do), a failed email never loses the request. `PATCH /v1/admin/tenants/:id` takes `name` and `defaultLocale` only (`plan`/`status` answer 400 `USE_SUBSCRIPTION_ROUTES`); suspension is `POST …/subscription/suspend` and `/unsuspend`.

15. **Plan numbers come from the environment (Phase 5A, decided 2026-10-21).** The twelve `PLAN_*` variables (six since Phase 5A, six for agents and phone numbers since Phase 5B-1; Env paragraph; `src/billing/plan-catalog/plan-catalog.env.ts` is the one list) are optional whole numbers, validated at boot through `planCatalogProblems` in `env.validation.ts` (digits only, empty = unset, minutes 0 to 1,000,000, agents and numbers 0 to 10,000, money 0 to 2,000,000,000 because the money columns are 32-bit; the error names the variable, never the value). `PlanCatalogSyncService` (own module, `OnApplicationBootstrap`) writes only the variables that are SET into the matching `plans` row (an entitlement key inside the JSON, or `price_minor` / `yearly_price_minor`) in one transaction under `pg_advisory_xact_lock(PLAN_CATALOG_LOCK_KEY)`, logs one structured line per change (`plan`, `field`, `from`, `to`) after the commit and nothing when nothing changed, and does not touch the database when no variable is set. The `plans` table stays the single source of truth: nothing else reads the variables. Remember: changing a variable and restarting changes the limits and prices of EVERY tenant on that plan at once (entitlements are read live; other instances within their 30 s cache); invoices already recorded are never touched; all instances must run with the same values (the one that starts last wins); while a variable is set, a hand edit of that one field in the table is undone at the next start (unset the variable to take manual control; a tenant-specific number goes through `entitlementsOverride`); a failed sync refuses the boot. The test setups blank the variables (`test/setup-env.ts`, `test/db/setup-db-env.ts`) because `.env` may hold real ones.

16. **Agents (Phase 5B-1, L7, decided 2026-10-28).** An *agent* is the TENANT's own setup (settings, knowledge, hours, greeting, voice, forwarding contacts) that the one shared engine uses for a call: it is not a separate AI and not the staff role named `agent` (routes, entities and tags say `agents`/"Agents" for the setup, "agent (staff role)" for the role; the role is not renamed). *Identity:* table `agents` (`active`|`disabled`, `is_default`); exactly one default per tenant (partial unique index; created in the signup transaction through `AgentProvisioningService`, backfilled by the data migration), a name unique per tenant ignoring case, never deleted when it is the default, never disabled or deleted while it has phone numbers (`AgentNumbersCheck`, Phase 5D plugs in and makes `phone_numbers.agent_id` RESTRICT). Every query carries `tenantId`; an agent of another tenant is 404 `AGENT_NOT_FOUND`. Audit entries (`agent.created|renamed|disabled|enabled|deleted|settings_updated`) hold names, status and version numbers only. *Limits:* entitlements `agents` (disabled ones count) and `phoneNumbers`; creating takes the subscription row lock via `EntitlementsService.assertCountAvailable` (403 `PLAN_LIMIT_REACHED` with `details {limit, used, max}`); lowering a limit never deletes anything. *Settings:* `agent_settings` holds one append-only row per version (a trigger refuses UPDATE; the highest version is current; rows go with their agent); a save (`PUT`, `expectedVersion` required, 409 `AGENT_SETTINGS_VERSION_CONFLICT`) validates OUTSIDE the transaction through `AgentSettingsValidator` (structural only: the field list, `collect`, capabilities and voice ids are the ENGINE's and `collect` is opaque JSON, never hard-coded) and inserts n+1. The document can hold forwarding phone numbers: owner/admin only, never logged, never in an audit entry. *The engine's pull:* `GET /internal/tenants/{tenantId}/agents/{agentId}/config` is the ONLY way settings reach the engine (never in a call ticket, URL or provider); service token via `InternalTokenGuard`, tenant AND agent checked together (one 404 for every miss), ETag/304, `Cache-Control: private, max-age=60`, a disabled agent answers 200 `status: "disabled"`, rate limited per tenant; read it only through `AgentConfigService` so the mock engine proves what the route returns. The route is outside `/v1` (listed in `configureApp`'s prefix exclusions) and not in the public OpenAPI; its contract is `backend-internal.openapi.yaml`.

17. **Requests and the status check (Phase 5B-2, his B1 and B4; built against the draft contract and the mock engine, NOT confirmed by the engine owner).** A *request* is what the AI took on a call (an appointment or a call-back) that staff confirm: the AI saves it as `requested` and never books or confirms anything (L1). *The table:* `requests` (one row per request; `reference` unique per tenant and drawn by the ENGINE, stored trimmed and upper case; `submission_key` unique per tenant; `details` = the engine's opaque document, 16 KB at most, personal data: never logged, never in an audit entry, a notification or a live message); composite foreign keys `(tenant_id, agent_id)` and `(tenant_id, end_customer_id)` make it impossible to name another tenant's agent or customer; all RESTRICT, so **an agent that has requests cannot be deleted** (409 `AGENT_HAS_REQUESTS` through `AgentRequestsCheck`, decided 2026-10-29; it can be disabled instead, and so can the default agent). *The workflow* is the pure `requests/state-machine.ts` (add a move there with a table test, never inline): staff `requested → confirmed | cancelled`, `confirmed → done | cancelled | requested`, `done → confirmed`, `cancelled → requested`; the engine may only change details or withdraw (`→ cancelled`) while the status is `requested`. Every write is a conditional update (`WHERE id AND tenant_id AND status = :the status that was read`) so races lose cleanly: staff get 409 `REQUEST_STATUS_CONFLICT` (a colleague was first, the status is already that, or `expectedStatus` is stale; `details.currentStatus`) or `REQUEST_TRANSITION_NOT_ALLOWED`; the engine gets 409 `REQUEST_LOCKED` (his `locked`) once a person acted. *The engine's routes* (outside `/v1`, `InternalTokenGuard`, rate limited per tenant, tenant from the verified path, agent and customer looked up UNDER it, errors `{statusCode, code, message}` unlike the engine's own `{error}`): create is idempotent by `(tenant, submissionKey)` (201 `created: true`, repeat 200 `created: false` with the SAME request, even in parallel), a reference taken by another request is 409 `REQUEST_REFERENCE_TAKEN` (the engine draws another and repeats with the same key), the customer upsert is by E.164 number (`end_customers.external_id = phone_<E.164>`, name and language only filled in when empty, never logged, never in a URL). The routes are the SOURCE OF TRUTH for a request; the events `record.submitted` / `record.updated` only make sure the team was told (notification `request.submitted` per active staff member and live `request.created` / `request.updated` are once-only through dedupe keys, ids only). *Staff* (`/v1/tenants/:tenantId/requests`, every role incl. the staff role `agent`): the list leaves out `details`, search is the reference, the customer's name or their phone number, every status move is audited (`request.confirmed|done|cancelled|reopened`, ids and statuses only; the staff note is never copied). *The status check* `GET /internal/tenants/{tenantId}/status?agentId=` decides ONLY through `EntitlementsService` (effective subscription: `voice`, `callMinutes`, `past_due` served within the allowance and never into overage) and the agent, in this order: `unknown_tenant` (a normal 200), `suspended` (suspended, closed, or no subscription: fail closed), `unknown_agent` (an agent that does not exist OR is another tenant's: ONE answer, `agentId: null`), `agent_disabled`, `quota_exceeded`; `unpaid` stays reserved. It answers live, with `Cache-Control: private, max-age=10`, and carries `overage: true` when the call is served only as billed overage. The mock engine's `simulateCall` asks the very same services, so a test through the mock proves what the routes do.

Exceptions: `password_resets` and `email_verifications` cascade with their user (ephemeral data), as do `notifications` and `stream_tickets` (the tenant side stays RESTRICT), and `audit_logs`/`staff_invites` reference the tenant with RESTRICT but their user columns are plain text without FK.
