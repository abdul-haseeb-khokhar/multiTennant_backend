# CLAUDE.md: multiTennant_backend

Backend core of a multi-tenant **AI customer-support platform** (call centres and businesses put an AI agent in front of their customers; humans take over when needed). This repo is the **backend core** only. Full design: [docs/architecture.md](docs/architecture.md). Open decisions with the other teams: [docs/team-alignment.md](docs/team-alignment.md). Read both before building features; the phase plan is in [docs/backend-roadmap.md](docs/backend-roadmap.md).

## Team split
- **Backend core (this repo, Abdul Haseeb):** tenants, auth, users/roles, end customers, keys, channel connections, agent config, plans/usage, gateway + dashboard API.
- **AI engine (Abdullah Younas, separate repo):** conversations, messages, RAG/knowledge chunks (pgvector), LLM, call logs, agent actions, voice. Schema `ai_engine` in the **same Postgres**; separate Prisma project.
- **Frontend (another colleague):** dashboard + widget; consumes this repo's OpenAPI.

## Stack and commands
NestJS 12, TypeScript 6, Prisma 6 (PostgreSQL, schema `tenant_core`), Passport JWT, bcrypt, class-validator/transformer, `@nestjs/config`, `@nestjs/swagger`, Jest 30, oxlint, Prettier (single quotes, trailing commas).

API: everything is under `/v1` except `GET /health` and `GET /health/ready`. OpenAPI UI at `/docs`, JSON at `/docs-json`, static copy in [docs/openapi.json](docs/openapi.json). CI: `.github/workflows/ci.yml`.

Env (`.env`, never commit or print values; names are listed in `.env.example` and validated at boot by `src/config/env.validation.ts`, which refuses to start without a `JWT_SECRET` of 16+ characters): `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN` (default `1d`), `PLATFORM_JWT_EXPIRES_IN` (default `1h`), `FRONTEND_URL` (the CORS origin and the base of emailed links; unset = no browser origin allowed; required when `NODE_ENV=production`), `MAIL_MODE` (`console` default; `link` also returns invite/reset/verification links in API responses for development, and the app refuses to start with `link` when `NODE_ENV=production`), `BILLING_JOB` (`on` default / `off`) and `BILLING_JOB_INTERVAL_MINUTES` (default 60) for the plan-transition job, `ENGINE_MODE` (`mock` default outside production, `http` required in production; `http` needs `ENGINE_BASE_URL` and an `INTERNAL_API_TOKEN` of 32+ characters), optional engine timeouts `ENGINE_FIRST_TOKEN_TIMEOUT_MS` (5000), `ENGINE_TOTAL_TIMEOUT_MS` (30000), `ENGINE_REQUEST_TIMEOUT_MS` (10000) and `MOCK_ENGINE_TOKEN_DELAY_MS`, `TRUST_PROXY` (number of proxies in front of the app, or a list of addresses/CIDRs/`loopback`; unset trusts nobody; `true` is refused because it trusts a forgeable header; set it to `1` behind the dashboard's server so audit `ip` and per-IP limits see the real client), `ESCALATION_RETRY_JOB` (`on` default / `off`) and `ESCALATION_RETRY_INTERVAL_SECONDS` (default 60) for the undelivered-escalation retry, optional `PORT`. `INTERNAL_API_TOKEN` also verifies the signed events the engine pushes to `POST /internal/events` (without it that route answers 503).

## Rules for this codebase
1. **Tenant isolation is the top rule.** Every query on tenant data includes `tenantId` in the `where`. Services take `tenantId` as the first argument. The tenant comes from the verified JWT/key, never from request content. After a scoped `findOne`, still scope the mutation (`update({ where: { id, tenantId } })`). Public token flows (invite accept, reset, verification) take the tenant from the record the hashed token belongs to.
2. Tenant-scoped routes live under `/v1/tenants/:tenantId/...` and use `@UseGuards(JwtAuthGuard, RolesGuard)`. `JwtAuthGuard` rejects a token whose `tenantId` differs from the URL (403 `TENANT_MISMATCH`) and a suspended tenant (403 `TENANT_SUSPENDED`). `RolesGuard` fails closed: every handler needs `@Roles(...)`. Platform-admin routes (`/v1/admin/...`) use `PlatformJwtAuthGuard`; the two token kinds are not interchangeable (`scope` claim: `tenant` or `platform`). `request.user.role` comes from the database (JwtStrategy), not from the token.
3. Never return `passwordHash` or `tokenHash`; use `omit: { passwordHash: true }` / `omit: { tokenHash: true }`.
4. Map Prisma errors in the service with `isPrismaError`: `P2002` → 409, `P2003`/`P2025` → 404 (`P2003` on tenant delete → 409 `TENANT_HAS_DEPENDENCIES`). Throw `ApiException(status, ErrorCode.X, message)` so the body is `{statusCode, code, message}`; add new codes to `common/errors/error-codes.ts` **and a translation to `src/lang/en/errors.json` and `ur/errors.json`** (a unit test fails otherwise) and never rename one (the frontend translates them).
5. **One writer per table.** Do not write to `ai_engine` tables; do not declare `ai_engine` models in this Prisma schema.
6. New tables go in schema `tenant_core` (`@@schema("tenant_core")`, `@@map` snake_case, columns `@map` snake_case).
7. Match surrounding style; run `npm run lint`, `npm test`, `npm run test:e2e` and `npm run build` before finishing. Lists return `{data,total,skip,take}` (default `take` 20, max 100). After changing a route or DTO run `npm run openapi:export`.
8. Role matrix (B2) as built: owner and admin invite staff and manage users (email, role, status, delete); an admin cannot invite, change, disable or delete an owner or promote anyone to owner; a tenant always keeps one **active** owner; every role reads users and reads, creates and edits customers; only owner/admin delete customers and read the audit log. Roles are `owner`, `admin`, `agent`. Nobody sets another person's password (invite, reset).
9. Emails are stored trimmed and lower-case (DTO `@NormalizedEmail`, services normalise too, and a DB CHECK constraint enforces it): normalise any new email input. A change that must not be half-done (role or status change plus its audit entry, the last-owner check) runs in one transaction and passes `tx` to `AuditService.record`. Never put tokens, hashes or links in logs (only `ConsoleMailer` may log a link) or in audit `before`/`after` (keys such as `password`, `token`, `hash`, `link` are stripped anyway).
10. **Billing (section I, Phase 2B).** The `subscriptions` row is the source of truth; `tenants.plan` and `tenants.status` are **denormalised mirrors** (`status`: `trial` = on Starter, `active`, `suspended`, `closed`) written ONLY by `SubscriptionService`, in the same transaction as every subscription change. Never write them anywhere else and never read them to decide what a tenant may do (ask `EntitlementsService.check`); the only reader is the auth guard (suspended/closed). Every change to a subscription is a normalised billing event through `SubscriptionService.applyEvent` (idempotent by provider event id, one transaction: state, invoice, append-only `billing_events` row, audit entry, mirrors). Transitions live in the pure `state-machine.ts`; add a transition there with a table test, never inline in a service. Time comes from the injectable `Clock`; code that reads a subscription uses `getEffective` (applies due transitions on read), never the raw row. Amounts are integer minor units plus a currency code, never floats. Entitlement keys and shapes: `billing/entitlements/entitlements.ts`. Nothing outside `ManualProvider` and `BillingProviders` may name a payment company (a unit test scans `src/`). `data_use_consents` only records the choice: no training export may be built before the legal review (I11).
11. **Gateway and widget (Phase 3).** Widget routes (`/v1/widget/*`) are public and take the tenant ONLY from the widget key (session) or the signed widget token (everything else), never from the body, URL or message text; the engine's `X-Tenant-Id` is that same verified value. The widget token has `scope: "widget"`, claims `tenantId`, `endCustomerId`, `conversationId`, `keyId`, is signed with a secret derived from `JWT_SECRET` (so staff and platform guards cannot accept it and it cannot pass as one), and `WidgetAuthGuard` re-checks the key (revoked?) and the request `Origin` against that key's `allowed_origins` on EVERY call; a missing Origin is refused. A widget key is public, not a secret; it is stored as sha256, shown once, never logged. Conversations are looked up by tenant AND end customer AND conversation id. **The end customer is never dropped (I5, D7):** a suspended/closed tenant or a plan without chat answers `200 {status:"blocked"}` with a fallback text and no token; a plan limit stores the message with `aiReply:false`, escalates with `limit_reached` and never calls the model; a slow or failing engine ends in `fallback ai_unavailable` plus an escalation (remembered in `gateway_conversations.escalation_pending` if the engine cannot be told). Fallback reason codes (`service_unavailable`, `limit_reached`, `ai_unavailable`) are stable, translated in the `widget` namespace, and never reveal billing state to the customer. **CORS** for `/v1/widget/*` is decided by `WidgetCorsService` (installed as the `enableCors` delegate in `app.setup.ts`): the preflight is answered only for an origin some active widget key lists (a deliberate cross-tenant boolean lookup, cached and rate-limited), and the real response gets `Access-Control-Allow-Origin` only after key and origin matched for that key; never `*`, never credentials; dashboard routes keep `FRONTEND_URL`. **Usage:** `usage_daily` is written only by `UsageService`, always through the `usage_events` ledger (unique per tenant, kind, engine id), so a conversation or message counts once; `EntitlementsService` reads `conversations` from it (`month` = UTC calendar month, `total` = since the UTC day the period began). The engine is reached only through `EngineClient`; never log message text, tokens or keys; engine error details never reach a customer.
12. **Human hand-off, live streams, notifications (Phase 4).** Conversations belong to the engine and are reached only through `EngineClient` (list, counts, claim, release, resolve, human message), always with the tenant of the verified staff token and the acting user's id and role; a conversation id of another tenant is a 404. The role rules live in `ConversationsService` AND are enforced again by the engine: every role may read, claim and work conversations; **only the assignee of a `human_active` conversation may reply, release or resolve it, whatever their role** (409 `CONVERSATION_NOT_ASSIGNED_TO_YOU`), a second claim is 409 `CONVERSATION_ALREADY_CLAIMED` (re-claiming your own is a no-op), a resolved one 409 `CONVERSATION_RESOLVED`; claim, release and resolve are audited (`conversation.claimed|released|resolved`, never message text); disabling or deleting a user returns their chats to the queue (best effort). Dashboard views show an anonymous visitor as `web_ab12cd…` only (`displayExternalId`): the full visitor id is that visitor's secret. **Events** come in at `POST /internal/events` (outside `/v1`, the only such route besides health): HMAC-SHA256 signature over `<timestamp>.<raw body>` with `INTERNAL_API_TOKEN`, 5 minute window; the tenant is the ENVELOPE's and is checked against an existing tenant, ids inside `data` are only looked up scoped to it; the (tenant, event id) row in `engine_events` is written in the same transaction as the effects (idempotent, rolls back whole); live messages and `announce` run after the commit; unknown types are acknowledged and ignored. Message text travels only as `human`/`system` `message.created` and only to the widget stream, never to the dashboard stream, the inbox or a log. **Streams** (`RealtimeHub`, in process): staff stream with Bearer header or single-use ticket (never the access token in a query string), 5 per user (the oldest is closed), re-checks the user every minute, ends after 1 hour; widget stream uses `WidgetAuthGuard` (key + Origin every call), ends with the token and re-checks the key. **Notifications**: one row per recipient created inside the event's transaction (escalated -> all active staff, assigned -> the assignee unless they assigned it to themselves, action.proposed -> owners/admins) or by `BillingRemindersService` from the hourly billing job with a `dedupe_key` (7/3/1 days, grace started, downgraded, 80%/100% of the conversation allowance); text is never stored: the frontend renders `<type>.title|body` from the `notifications` namespace with `params` (documented per type in `notification-types.ts`); every query is scoped to tenant AND user.

- Do **not** run `prisma migrate reset` or `db push` against the shared database. See A2 in team-alignment (separate `?schema=` per project, to be verified).
- `tenant_core` migrations must run before `ai_engine` migrations (their FK points here).
- `ON DELETE RESTRICT` everywhere: tenant removal follows the offboarding procedure (architecture §5.6). Exceptions: `password_resets` and `email_verifications` cascade with their user (ephemeral data), as do `notifications` and `stream_tickets` (the tenant side stays RESTRICT), and `audit_logs`/`staff_invites` reference the tenant with RESTRICT but their user columns are plain text without FK.
- The DB currently configured in `.env` is `multitenant`; the AI side uses `caller-ai-agent`. Pending decision A1.
- Generate migrations against a **throwaway** Postgres (`DATABASE_URL` pointing at it, `prisma migrate dev --create-only`), read the SQL, then `prisma migrate deploy` on the real database. Check the generated folder name sorts after the previous migration. CI applies all migrations to a throwaway Postgres, fails if `schema.prisma` has changes without a migration, then runs `npm run test:db`.
- The audit log is append-only by a DB trigger; anything that must delete from it (offboarding, retention) is a privileged maintenance step.

## Known issues
Phases 0 and 1 closed the original account-lifecycle issues (unprotected `/tenants`, unenforced roles, deleted/demoted users keeping a valid token, passwords set for other people, non-atomic last-owner check, case-sensitive emails, and the rest). Still open:

1. No refresh tokens or login throttling (Phase 8). Password-reset throttling exists but its counters are in process memory, so with several instances each counts on its own (move it behind Redis with the rest of Phase 8). Behind a reverse proxy set `TRUST_PROXY` (Phase 3B), otherwise every request counts as the proxy's IP.
2. No real mail provider yet (H3; **Resend chosen 2026-10-10**, built in Phase 4C, starting in test mode with `onboarding@resend.dev`, which only delivers to the Resend account's own address): invite, reset and verification links are logged by `ConsoleMailer`, or returned in the response with `MAIL_MODE=link` in development. Choose a provider and sender domain, implement `Mailer`, render the `email.<template>.*` keys of the `notifications` namespace, bind it in `MailModule`. Until then nobody receives an email.
3. In-app notifications (H5) are built (Phase 4, issue 13). The Urdu translations (`src/lang/ur`) were written by an AI and reviewed as fine by the owner; new keys (including every Phase 4 notification, widget and error text) still need a native-speaker check.
4. Users that existed before Phase 1 have `email_verified_at = NULL`, so an existing owner cannot invite until they verify (`POST /v1/auth/verify-email/resend`; the link is in the log or, with `MAIL_MODE=link`, in the response). Not backfilled on purpose: nobody verified anything.
5. "An unverified owner cannot change plan" is enforced by `EmailVerifiedGuard` on invites only: tenants have no plan-change route yet (platform admins change plans). Put the guard on that route when it exists (Phase 5).
6. Tenant hard delete (`DELETE /v1/admin/tenants/:id`) only succeeds for a tenant with no users, customers, invites, API keys, usage rows, notifications, engine events or audit entries (`RESTRICT`; the audit log is append-only by trigger). The real offboarding procedure (architecture §5.6) is Phase 8 and must drop that trigger as a privileged step; so must the 12-month audit retention purge.
7. The e2e tests run against mocked Prisma; SQL, constraints, the audit trigger and migrations are exercised by `npm run test:db` and the CI `migrations` job (`migrate deploy`, drift check, then the DB-backed tests). The DB suite refuses anything but `TEST_DATABASE_URL` and leaves its data behind (tenants cannot be deleted), so use a disposable database. Its last-owner race test demonstrates the invariant; it does not prove the isolation level on its own.
8. Migration `20261007100000_add_tenant_slug_and_platform_admins` backfilled `slug` for existing tenants as `<name>-<first 8 chars of id>` (rename of a slug is not exposed yet). The Phase 1 migrations `20261007120000_phase1_account_team` and `20261007120100_normalize_emails`, the Phase 2B migration and `20261008100000_phase3_gateway` are applied to the local `multitenant` database (a pre-Phase-1 `pg_dump` of `tenant_core` is in the Phase 1 session's scratchpad); any other database needs `prisma migrate deploy`. The second refuses to run, and names the rows, if lower-casing would make two emails collide.
9. `oxlint` could not run on the Windows machine that built Phases 0 and 1 (an Application Control policy blocks its native binary); it runs on the machine that built Phases 2B and 3 (0 errors, a few `unbound-method` warnings in specs). Prettier flags CRLF working-tree files on Windows (`core.autocrlf`): check with `npx prettier --check --end-of-line auto "src/**/*.ts" "test/**/*.ts"`; CI (Linux) checks the real thing.
10. The Prisma mocks do not apply `omit`: a mock that echoes `create` data back must strip `passwordHash`/`tokenHash` itself (see the e2e mocks); the unit tests assert the `omit` argument instead.
11. Billing known issues (Phase 2B built, details in docs/backend-roadmap.md):
    - **Tax and invoice wording (I7) stay open for the accountant**: invoices have no tax lines, numbers are `INV-<calendar year>-<6 digits>` (a fiscal year may be wanted), no PDF/HTML view. **Training use of conversations (I11) stays blocked on legal review**: only the consent record exists.
    - **Seats and conversations** are really enforced (conversations from `usage_daily`, written by the Phase 3 gateway, checked when a conversation starts). `knowledgeMb` still goes through `UsageProvider` and reports 0 until knowledge upload (Phase 5). The entitlements cache is per instance (30 s, never past the next transition): another instance sees a change within 30 s (Redis invalidation: Phase 8).
    - A downgrade never removes anyone: users above the new seat limit stay, new invites/acceptances/re-enables are refused. Keeping over-limit content inactive for 60 days and the day 30/50/57 notices (I10) are not built; neither are reminders and in-app notifications (I8, need H5): `GET /v1/me` carries `daysLeft`, `graceDaysLeft` and the status so the dashboard can show a banner.
    - `account.closed` is handled by `applyEvent` but has no route yet (owner/admin close request and the 60-day deletion are Phase 8). `PATCH /v1/admin/tenants/:id` still accepts `plan` and `status` (deprecated): they are translated into `plan.changed` / `tenant.suspended` / `tenant.unsuspended` events; the tenant columns are never written directly.
    - One subscription row per tenant (history is `billing_events`, `invoices` and the audit log). Money columns are 32-bit integers (max PKR 21,474,836 per invoice; the DTO caps a payment at 2,000,000,000 minor units).
    - The job (`billing.scheduler.ts`) is a timer in every instance guarded by `pg_try_advisory_xact_lock`; correctness never depends on it. Starter and Free entitlement values are placeholders stored as data in `plans`.
12. Gateway known issues (Phase 3, details in docs/backend-roadmap.md and docs/contracts/README.md):
    - **Never run against the real engine.** The contract (docs/contracts/engine-internal.openapi.yaml) is the backend's proposal; two calls (`escalate`, `aiReply:false`) are additions to Appendix A that the engine owner has not confirmed; Phase 4 added more (issue 13). Everything is tested against the mock and a contract-faithful fake server only.
    - Rate limits (widget key / visitor / IP) live in process memory: per instance, multiplied by the number of instances until Phase 8. `req.ip` is the proxy's address unless Express `trust proxy` is set (so per-IP limits are shared behind a proxy). The conversation limit is a soft check at conversation start: parallel starts at the limit can overshoot by a few.
    - A customer message is lost when the engine cannot be reached (it is not stored anywhere on our side; the customer is told a colleague will reply). An escalation the engine could not be told about stays in `gateway_conversations.escalation_pending`; since Phase 4 `EscalationRetryService` retries it (10 attempts with a growing wait, then the flag stays; issue 13). A conversation started over the plan limit stays human-only for its lifetime.
    - `visitorId` is the only secret of a returning visitor (anyone who knows it can resume that chat); the widget token is 15 minutes and cannot be revoked one by one (revoke the widget key to end all its sessions). Origins are exact (`scheme://host[:port]`): no wildcards. `server` API keys can be created but no route accepts them yet. `usage_events` holds a row per counted message and has no retention purge yet; token counters are 32-bit.
    - The widget Urdu texts and the new Urdu error strings were written by an AI and need a native-speaker check. Tenant-specific greeting and fallback wording waits for `agent_config` (Phase 5; hook: `WidgetSettingsProvider`).
13. Human hand-off known issues (Phase 4 and 3B, details in docs/backend-roadmap.md and docs/contracts/README.md):
    - **Only the mock engine has run.** Everything the staff side needs from the engine (list, counts, claim, release, resolve, human messages, the `X-Acting-*` headers, the `CONVERSATION_ALREADY_CLAIMED|RESOLVED|NOT_ASSIGNED_TO_YOU` 409 codes) and the whole event receiver (names, payloads, HMAC signing) are PROPOSALS in docs/contracts/ that the engine owner has not confirmed. The dashboard stream, the notifications and the widget stream depend on the engine pushing events: if it does not, they stay silent (the widget can still poll `GET /v1/widget/conversation`, the dashboard can refetch).
    - The hub, the stream caps and every rate limit are in process memory: several backend instances need a shared bus (Redis, Phase 8) or a stream only sees events handled by its own instance. Stream tickets and the event inbox are in the database and work across instances.
    - A claimed conversation stays with its holder until they release or resolve it, or are disabled or deleted. There is no idle timeout and no transfer (J4, H8): an owner or admin cannot free a colleague's chat. If the engine is down while a user is disabled or deleted, the release is skipped (logged, not retried) and their chats stay claimed.
    - Notifications: recipients are decided when the event is processed (someone invited later does not get older ones); billing reminders come from the hourly job (up to an hour late; `period.ended` events are read back 7 days); no email or push; the day 30/50/57 data-deletion notices (Phase 8) and `invite.accepted`, `ingestion.failed`, `tenant.suspended` notifications do not exist yet (the first two have translation keys).
    - A browser `EventSource` that uses a ticket must ask for a new ticket for every reconnect (a ticket works once); a stream ends after an hour; `Last-Event-ID` resumes the last 100 events, older gives `resync`.
    - **The full widget visitor id is still returned by `/v1/tenants/:tenantId/customers`** (`externalId` = `web_<visitorId>`, to every role): it is that visitor's only secret (issue 12). Only the new conversation and notification views shorten it. Decide whether the customer API should do the same.
    - The 80% / 100% reminders and their texts assume a hard stop at the included conversations. Phase 4B (overage on by default for Pro, J6) must change `usage.limit_reached` (when overage is on the AI keeps answering) and add the "overage started" notification.
    - `conversation.created` events are acknowledged but do not count a conversation (the gateway does at start); only `usage.recorded` writes usage from events.
